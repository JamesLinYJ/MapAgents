## 第4页 · 预报员现在的难处

**页面标题：** 预报员每天面临的四个实际困难

**解决领导什么疑问：** 为什么要搞这个系统？现在的方式有什么问题？

**关键内容（四个痛点，每个配一句话案例）：**

1. **数据格式太多、太杂**
   - 雷达数据、模式数据、观测数据，光格式就有10多种
   - 每种数据要用不同的软件打开，预报员大部分时间不是在分析，而是在"打开→导出→转换→再打开"

2. **工具链太碎，数据靠手搬**
   - 做一张风险图：ArcGIS做空间叠加 → Python做统计 → Excel做表 → Word写报告
   - 四个软件之间靠人工导出导入，一步错了全部重来

3. **编码乱码，反复折腾**
   - 数据里的中文地名经常乱码（UTF-8、GBK各种编码混在一起）
   - 预报员不是学计算机的，遇到乱码只能一遍遍试，浪费时间

4. **每次新数据都要重做一遍**
   - 短临预报每5分钟来一批新数据，全部流程重跑
   - 换一个县、换一个阈值，也要从头来

**数据强化：** 单次出图30~60分钟，短临预报时效就几个小时——分析本身花一个小时，预报还有什么意义？

**关键内容：**

**数据强化：**
- 涉及45万个网格点
- 数据格式10多种
- 需要同时操作ArcGIS + Python + Excel + Word
- GIS和Python编程是必备技能，但区县预报员大多没有这个背景

## 第8页 · 场景二：降水排名表（传统方式）

**页面标题：** 一个县几百平方公里，只靠一两个站点代表全县雨量

**解决领导什么疑问：** 降水排名表是什么？传统做法哪里不准？

**关键内容：**
- 业务场景解释：短临预报中，区县预报员需要把全县降雨量算出来，做等级排名，发给决策部门
- 传统做法的问题：
  - **"以点代面"** —— 一个县几百平方公里，预报员只能靠这个县1到2个气象站的雨量来代表全县
  - 浙江是丘陵地形，一座山相隔的两个县，降雨时间能差**6到12个小时**
  - 山区暴雨时，山顶和山谷的降雨量相差好几倍
  - **低涡型暴雨的漏报率高达75%**（公开文献数据）——强降水空间尺度小、来得快去得快，传统方法很难抓到
- 更痛苦的是：每**5分钟**来一批新数据，所有计算、制表、调格式全部手工重做

**数据强化：**
- 90个区县（浙江省）
- 每县仅1~2个观测站
- 山两侧降水时差6~12小时
- 低涡型暴雨漏报率75%
- 数据5分钟刷新一次，每次全重做

**过渡到第9页：** "我们的做法完全不同——不是选几个代表点，而是全部算进去……"

- 每个结果可验算——哪个县、哪个格点的数据都能查，支持手算核对

## 第12页 · 安全和可靠性

**页面标题：** 安全可靠吗？数据会不会丢？

**解决领导什么疑问：** 这个系统安不安全？数据丢了怎么办？出错了找谁？

**关键内容：**

**安全方面——七层防护（用形象比喻，不列技术术语）：**

| 防护层级 | 大白话解释 |
|---------|-----------|
| 1. 通信加密 | 数据和外界传输全程加密，外人看不到 |
| 2. 身份认证 | 每次操作都要确认是你本人 |
| 3. 频率控制 | 防止恶意高频调用 |
| 4. 实时校验 | 每笔操作的合法性和时效性实时检查 |
| 5. 权限分级 | 50多种操作各有独立权限，不是简单的管理员/普通用户二分 |
| 6. 高风险审批 | 涉及写文件、删数据、调外部服务的操作，必须预报员本人批准才能执行，且每次批准只能用一次 |
| 7. 执行隔离 | 所有计算在独立环境中执行，只能访问限定目录 |

- 七层任何一层拒绝即阻断——不依赖单一防线

**数据可靠性方面：**
- 系统在任何时刻崩溃，数据不丢、文件不坏
- 某个文件损坏不影响整体——系统能自动定位并跳过损坏部分
- 每个计算结果都可追溯：可以手算核对，有独立验证脚本

## 设计说明

**为什么这么设计：**
1. **前3页做认知铺垫** —— 领导对AI智能体零认知，直接从豆包和点外卖切入，降低理解门槛。不用解释"智能体"这个词，全程没出现过一次"智能体"
2. **2个核心场景各3页（痛-方-数）** —— 痛点一页引起共鸣，方案一页展示操作，数据一页提供量化支撑。三段式，每一段领导都能"听懂+看到数据"
3. **第11页项目进度** —— 用代码规模、工具数量、跑通链路回答"是不是真东西"。不用技术名词，只说业务链路
4. **第12页安全** —— 领导最关心的"出了事谁负责"。七层防护用大白话解释，不提任何安全协议或技术
5. **第13-14页未来+回报** —— 先画饼（未来三步走），再算账（投入回报），让领导觉得"有前景、划算"
6. **第15页请求** —— 这是最关键的一页。三个请求具体、可操作，领导可以直接在上面打勾
7. **全程没有出现过以下词汇**：智能体、大语言模型、架构、协议、API、SDK、算法、神经网络、WebSocket、PostGIS、JSON、容器、沙箱、编排——所有技术名词全部用大白话代替

**回答领导最关心的四个问题：**
- **省时间？** → 30~60分钟 → 10秒，180~360倍
- **准不准？** → 45万格点全量计算 vs 1~2个站点，告别"以点代面"
- **安不安全？** → 七层防护，每层独立，数据不丢不坏
- **进度到哪了？** → 5万行代码、6条链路已跑通、可以演示
