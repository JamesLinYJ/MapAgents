## 一、项目概述

### 1.1 一句话定义

> **GeoForge** 是一个**中文优先**的 **GIS Agent 平台**，将大语言模型（LLM）与空间地理信息系统（GIS）、气象科学计算深度融合，让用户通过**自然语言对话**即可完成复杂的空间分析和气象决策。

### 2.2 核心技术挑战

| 挑战 | 描述 | GeoForge 解决方案 |
|------|------|-------------------|
| **工具编排** | 15+ 个 GIS/气象工具如何让 LLM 正确选择和编排？ | valueRef 类型链 + 双射契约校验 |
| **空间数据** | GeoJSON/NetCDF/GeoTIFF 等多格式如何统一？ | 文件型事实源 + 内容寻址对象存储 |
| **实时交互** | Agent 长时间运行如何实时反馈给用户？ | WebSocket 控制面 + 事件总线推送 |
| **安全沙箱** | LLM 生成的代码/文件操作如何隔离？ | Docker Sandbox + 路径三层防御 |
| **科学计算** | Python 科学库与 Node 后端如何协作？ | 无状态 Sidecar Worker + HMAC 认证 |

## 四、核心技术创新

### 4.1 创新一：ToolProvider 双射契约校验 + valueRef 类型链

这是本平台最核心的架构创新。传统的 AI Agent 工具系统存在"文档说支持但实际不行"的契约漂移问题。

```
┌────────────────────────────────────────────────────────────────────┐
│                  ToolProvider 双射契约校验                           │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│   Manifest (声明)                    Runtime (实现)                 │
│   ┌──────────────────┐              ┌──────────────────┐          │
│   │ {                │              │ tools(): ToolDef[]{          │
│   │   id: "geo-...", │              │   {                           │
│   │   name: "...",   │              │     name: "...",              │
│   │   tools: [       │              │     label: "...",             │
│   │     { name,      │   双射校验    │     description: "...",      │
│   │       label,     │◄──────────►│     jsonSchema: {...},        │
│   │       desc,      │  validate   │     handler: async (args)     │
│   │       schema }   │  Manifest   │   }                           │
│   │   ]              │  Parity()   │ ]                             │
│   │ }                │             │                               │
│   └──────────────────┘              └──────────────────┘           │
│                                                                    │
│   使用 stableJson 深度比较 5 个字段                                   │
│   确保 UI/Agent 看到的公开契约与运行时实现绝不漂移                      │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
```

**valueRef 类型链** — 工具间数据传递的类型安全层：

```
┌──────────────────────────────────────────────────────────────────────┐
│                       valueRef Kind 链                               │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   工具 A: inspect_dataset                                            │
│   输出: { kind: "meteorological_dataset", refId: "ds_001" }          │
│                     │                                                │
│                     │  kind 约束匹配                                  │
│                     ▼                                                │
│   工具 B: compute_statistics                                         │
│   输入: dataset_ref (x-value-ref-kinds: ["meteorological_dataset"])  │
│   → requiredRefKind(ctx, args, 'dataset_ref',                       │
│                     ['meteorological_dataset'])                      │
│                     │                                                │
│                     │  kind 约束匹配                                  │
│                     ▼                                                │
│   工具 C: render_raster_map                                          │
│   输入: variable_ref (x-value-ref-kinds: ["meteorological_variable"])│
│                                                                      │
│   ──────────────────────────────────────────────────────             │
│   如果 LLM 错误地将 "nowcast_sequence" ref 传给需要                   │
│   "meteorological_dataset" 的工具 → requiredRefKind()                │
│   立即抛出异常: "必须引用 meteorological_dataset，实际为               │
│   nowcast_sequence" → Agent 重新选择正确工具                          │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 创新二：文件系统作为会话事实源

```
┌──────────────────────────────────────────────────────────────────────┐
│                  文件型会话存储 vs 传统数据库存储                       │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   传统方案 (Postgres 存一切):                                         │
│   ┌──────────────────────────────────────────────┐                  │
│   │ sessions │ threads │ runs │ items │ events    │  DB 表           │
│   │  CRUD    │  CRUD   │ CRUD │ CRUD  │ CRUD     │  大量写入          │
│   └──────────────────────────────────────────────┘                  │
│   ⚠️ 转录本是最大写入量 → DB 瓶颈                                     │
│   ⚠️ 审计/回放需 JOIN 多表 → 性能差                                   │
│                                                                      │
│   GeoForge 方案 (文件是事实源，PG 是索引):                              │
│   ┌──────────────────────────────────────────────┐                  │
│   │ runtime/conversations/                        │                  │
│   │   {sessionId}/                                │  文件系统         │
│   │     {threadId}/                               │  唯一事实源       │
│   │       transcript.jsonl  ← 追加写入，不可变     │                  │
│   │       items.jsonl        ← 按 Run 分片        │                  │
│   │       events.jsonl       ← 审计事件           │                  │
│   │       checkpoints/       ← 断点续跑           │                  │
│   │       memory.md          ← 长期记忆           │                  │
│   └──────────────────────────────────────────────┘                  │
│   ┌──────────────────────────────────────────────┐                  │
│   │ Postgres                                      │  数据库           │
│   │ · 轻量索引 (O(1) 内存 Map 查找)               │  仅存可重建索引    │
│   │ · Tool Catalog · Runtime Config · Layers      │                  │
│   └──────────────────────────────────────────────┘                  │
│                                                                      │
│   优势:                                                               │
│   ✅ 写入路径简单 (fs.append) → 高性能                                 │
│   ✅ 天然可审计 (grep transcript.jsonl)                               │
│   ✅ 崩溃恢复简单 (Journal → 重放)                                    │
│   ✅ 无 DB 锁竞争                                                     │
│   ✅ 索引可随时从文件重建                                              │
```
